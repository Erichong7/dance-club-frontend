# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Frontend for a dance club practice-room scheduler ("댄스 동아리 연습 스케줄러"), built with React 18 + Vite + react-router-dom. It talks to a real Spring Boot backend at `localhost:8080` (proxied via `vite.config.js`'s `/api` proxy). Swagger/OpenAPI docs for that backend are served at `http://localhost:8080/swagger-ui/index.html` (raw spec: `/v3/api-docs`) — check them (and re-verify with `curl`, since the generated Swagger security annotations don't always match runtime behavior) before changing any `api.*` call shape.

## Commands

```bash
npm install
npm run dev       # starts Vite dev server on http://localhost:3000
npm run build     # production build
npm run preview   # preview the production build
```

There is no lint, test, or typecheck script configured in `package.json`. Do not assume `npm test` or `npm run lint` exist.

## Architecture

**Real backend, not mock-first anymore.** `src/api/client.js` exports `api.*`, one function per backend endpoint (auth, schedules, teams, performances, posts). `USE_MOCK = false`. Responses are the raw JSON body — the backend does **not** wrap responses in `{ data: ... }`. Auth is `POST /api/auth/login` with `{ email, password }` (not student ID) returning `{ accessToken, refreshToken }`; `accessToken` is sent as `Authorization: Bearer` on every request, and a 401 triggers one silent `POST /api/auth/reissue` (via the `Refresh-Token` header) + retry before giving up. **Only 401 clears the session** — this backend returns bare 403s (empty body) for both "wrong password" and "authenticated but lacking permission", so treating 403 as a logout signal was tried and caused real bugs (a single not-yet-implemented endpoint 403'ing would nuke a just-created session). If you touch `request()` in `client.js`, keep that distinction.

**Signup is approval-gated, and `SignupRequest` has 5 required fields.** `POST /api/auth/signup` takes `{ email, password, passwordConfirm, nickname, phoneNumber }` — `passwordConfirm` must match `password` (else `409`/`400` with `PASSWORD_CONFIRM_MISMATCH`) and `phoneNumber` must match `^01[016789]-\d{3,4}-\d{4}$` (e.g. `010-1234-5678`). A successful signup doesn't log the user in — it creates a `REQUESTED` row that an admin must approve via `admin/SignupRequests.jsx` (`PATCH /api/auth/{id}/approve|reject`) before login works; `Login.jsx` shows dedicated copy for the `SIGNUP_PENDING`/`SIGNUP_REJECTED` error codes in the meantime.

**Which endpoints need login is defined by the backend's `SecurityConfig`** (`global/security/SecurityConfig.java`, `authorizeHttpRequests`), not by guessing from Swagger. Public (`permitAll()`, no token needed): `POST /auth/login|signup|reissue`, all of `GET /posts/**`, and single-segment `GET /schedules`, `GET /schedules/{id}`, `GET /teams`, `GET /teams/{id}`, `GET /performances`, `GET /performances/{id}`. Everything else — including nested paths like `GET /schedules/team/{teamId}` (two segments, doesn't match the `/schedules/*` matcher) and all writes — falls to `anyRequest().authenticated()`. This list expanded over time (it used to be posts-only); re-check `SecurityConfig` directly before assuming an endpoint needs a token, rather than trusting this doc or Swagger's lock icons.

**User profile comes from `GET /api/users/me`** (not `/api/auth/me` — that path never existed; profile lives under `UserController`, not `AuthController`) (`UserDetailResponse`): `{ id, email, nickName, role: 'ADMIN'|'USER', teamIds: number[], teamNames: string[] }`. Note it's `nickName` (capital N), and a user can belong to **multiple** teams — there's no singular `teamId`/`teamName`. Use `getMyTeams(user)` / `formatMyTeamNames(user)` from `src/utils/user.js` rather than reading `teamIds`/`teamNames` directly, so this stays consistent everywhere. If this endpoint call ever fails (network error, or the route changes again), `AuthContext` (`src/context/AuthContext.jsx`) falls back to decoding the JWT's `sub` claim for a minimal profile with `role: 'USER'` and no teams (see `isFallback` on the user object) — admin nav/pages are invisible in that fallback state, which is correct (don't "fix" it by hardcoding a role). If the fallback JWT decode *also* fails (e.g. a stale non-JWT token left over from an old build), `loadProfile()` clears the session and drops back to the login screen instead of hanging — this was a real bug once, don't reintroduce it by making `loadProfile` unconditionally resolve to "authed".

**Auth/user state lives in `AuthContext`,** not local `App.jsx` state. `useAuth()` gives you `{ user, isAuthed, isLoading, isAdmin, login, logout, refreshProfile }`. `App.jsx` has a single `Sidebar`+`Topbar`+`Routes` shell used whether or not you're logged in — `/login`/`/signup` are the only paths that opt out of it (sidebar-less full-screen cards). Everything else renders inside the shell, and each `<Route>` decides for itself whether it needs `isAuthed` (redirecting to `/login` if not) based on whether its underlying API calls are in the public list above — `/schedule` and `/notice` don't gate at all, `/`(dashboard)/`/apply`/`/photo` do. `Sidebar`/`Topbar`/`ProfileMenu` all accept `user === null` (logged-out) and swap the avatar/logout UI for a "로그인" button rather than crashing — don't reintroduce an assumption that `user` is always present in those components. Admin-only routes (`/admin/requests`, `/admin/signup-requests`, `/admin/performances`, `/admin/performances/:id`) are only registered when `isAdmin` is true.

**`Apply.jsx` is a multi-slot request cart, not a single form.** It holds an array of request cards (add/remove, each independently validated), matching the reference `dance-scheduler-design.html` mockup's flow — but unlike that mockup, there's no batch-create endpoint, so submit fires one `POST /schedules` per card via `Promise.allSettled` and renders a per-card success/failure receipt. The room field is a button+popover picker (`RoomPicker`, reusing the `.room-picker*` CSS classes) offering only a single "후보" room — the mockup's dual 희망/예비 picker doesn't apply since `ScheduleCreateRequest` has just one room field (see below). Team/performance dropdowns are independent (not cascading) since the API doesn't link teams to specific performances.

**Only a team's `LEADER` or `DEPUTY` can create schedules — a plain `MEMBER` gets a 403.** Confirmed by direct testing against the live backend (not documented anywhere in Swagger/CSV): `POST /api/schedules` 403s for a team member added with `role: "MEMBER"`, and succeeds once promoted to `LEADER` or `DEPUTY` via `PUT /api/teams/{id}/members/{userId}/role`. The frontend doesn't (and can't cleanly) pre-check this — a MEMBER will see the request UI and only find out via the per-card error message after submitting. If you add a team-role field to `UserDetailResponse` later, this would be worth surfacing earlier.

**Domain rules live in `Apply.jsx`, not the backend (yet).** The scheduling rules — 2-hour daily cap per team, cheer room (`CHEER_ROOM`) locked to Wednesdays 18:30–20:30, applications close the Sunday before the practice week — are implemented as a pure `validate(form)` function directly in `src/pages/Apply.jsx`. This must mirror the backend's `ScheduleValidationService` once it exists. Note `ScheduleCreateRequest` only has one room field (`alternativeRoom`, a candidate room) — there's no separate "preferred vs. backup" pair; final room assignment happens later via the admin-only assign/reassign endpoints.

**Room types are the backend's enum, not a frontend invention.** `roomLabels`/`roomOrder` in `mockData.js` are keyed by the backend's actual enum values (`CLUB_ROOM`, `CHEER_ROOM`, `STUDENT_UNION_BASEMENT`, `EXTERNAL`, `UNDERGROUND_PARKING`), each mapped to a Korean label. `Schedule.jsx`'s `roomColor` map (and `admin/Requests.jsx`'s local copy) is keyed the same way. Adding a new room type means updating all of these together with whatever the backend adds.

**"공지사항" (Notice) is the backend's generic Post CRUD, not a specialized notice board.** There is no "긴급/공지/안내" type field on posts — that was a frontend-only decoration in an earlier prototype and has been dropped. `Notice.jsx` handles both the list (`/notice`) and detail (`/notice/:id`) views based on whether `useParams().id` is set; write/edit/delete are gated behind `isAdmin`.

**Photo board has no backend at all.** `Photo.jsx` is intentionally mock-only (`mockPhotos` in `mockData.js`) and visibly labeled "프로토타입" in the UI. Don't wire it to a real endpoint unless one gets added to the backend — there isn't one today.

**Team/performance/schedule admin flow matches what the API actually supports, not what the design mockup implies.** There's no "approve a single pending request" endpoint — approval only happens via `POST /schedules/assign` (bulk, auto-assigns every PENDING schedule in a performance+week) or `POST /schedules/assign/manual` (admin creates+assigns a brand-new schedule directly, bypassing the request flow entirely). Individual actions available on an existing schedule are: reject (PENDING only), cancel, delete, and reassign room (`PUT /schedules/{id}/room`, only meaningful once a room is assigned). `admin/Requests.jsx` reflects exactly this — don't add an "approve one" button, the backend can't do it.

**A user-search API now exists** (`GET /api/users/search`, admin-only, filters by `nickname`/`email`/`signupStatus`) — wired in as `api.searchUsers()` in `client.js`. It's used by the `MemberSearch` autocomplete in the team-member-adding flow and by `admin/SignupRequests.jsx`'s approval queue. `addTeamMember`/`POST /teams/{id}/members` still takes a raw numeric `userId` in its body, but the UI no longer requires typing it blind — `MemberSearch` resolves a name/email to that ID first.

**Styling is CSS custom properties + hand-written classes, no CSS framework.** `src/styles/tokens.css` defines design tokens (colors, fonts, radii) as `:root` variables; `src/styles/app.css` holds component classes like `.card`, `.form-grid`, `.btn`, `.event-block`, `.receipt-table`, `.list-row-inline`. Components use these class names directly rather than inline styles or a utility framework — follow that convention for new UI. (There's also a separate one-off `dance-scheduler-design.html` mockup floating around the repo/conversation history — that's a static Pretendard/purple-themed reference for screen flow only, not a stylesheet to import; the actual app's design system is `tokens.css`/`app.css`.)

**Language:** UI copy, code comments, and README are in Korean. Match this when editing existing files.
